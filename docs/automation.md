# 自动签到实现说明

自动功能默认关闭，用户保存每日北京时间后生效。本文描述 1.1.0 的实现，真实签到要求以学校规定为准。

## 调度与任务有效性

`ScheduleWorker` 不要求网络，先持久安排下一次日历时间，再派发要求联网的 `AutoCheckinWorker`。任务按设置版本、账号代次和执行时间唯一命名，重复安排使用 KEEP。进程启动和系统时间变更时核对已有任务。延迟跨越多个周期时只评估最近一次已到点的周期；保存设置前的周期不会补跑。

修改设置增加版本；清除或更换账号增加代次。旧任务在启动和提交前都检查版本、代次和开关。取消 WorkManager 任务之外，还以数据库检查作为提交前的最后一道约束。签到设定时间必须落在服务器当前返回的学校窗口内，避免上一天的任务误处理次日计划。

## 统一入口与防重

应用级 `CheckinCoordinator` 使用协程 Mutex 串行处理手动操作和 Worker 的登录、查询及提交。Cookie 和 Token 仍只保留在内存。ViewModel 观察协调器的查询状态和数据库设置，使用原子 StateFlow 更新，避免后台结果覆盖设置更新。

`SubmissionGuard` 在 Repository 已重新查询并完成位置检查后、调用 `clockIn.action` 前运行。它检查协程取消状态、自动任务版本、校内方式、服务器时间和窗口，然后同步登记提交。数据库事务失败时不发送请求。

防重键为账号摘要、计划 ID 和学校签到窗口起点。跨午夜的窗口归属开始日；学校原始时间字段仍原样用于协议加密和提交。

| 本机状态 | 含义与后续操作 |
|---|---|
| DISPATCHING | 请求即将或已经发出；重启后一律按待确认处理 |
| PROCESSING | 学校仍在处理，仅查询 |
| UNKNOWN_RESULT | 响应或确认不完整，仅查询 |
| SUCCESS | 学校查询已确认成功，禁止重复提交 |

重新登录、修改时间不会清除记录。不同学校窗口有独立键，昨天的未知结果不会永久阻止今天。清除本机数据或卸载会移除本机保护记录，重新登录后应先核实学校状态。

## 重试、暂停和通知

提交前的网络失败最多尝试三次，WorkManager 指数退避约 5、10 分钟，次数同时保存到数据库。超过当前周期或学校时段不再提交。服务器时间不可用不采用手机时间替代。

提交后立即查询；仍未确认时，`ConfirmWorker` 只查询，后续最多两次，延迟约 1、5 分钟。查询次数也持久保存。计划已变化时不能把新计划的成功视为旧提交成功。认证或验证码错误暂停自动功能，用户成功登录后仍需明确恢复。

结果通知权限可拒绝，拒绝不影响设置和执行。通知不包含账号、认证数据或详细地址。没有精确闹钟或常驻前台服务，系统省电和后台限制可能导致延迟；强制停止后需打开应用恢复调度。

## 验证

AutomationTest 覆盖执行决策、持久化、重试、并发、最终提交检查和崩溃恢复；SchedulerTest 检查唯一任务、网络约束和取消；Compose 与真机测试使用虚构状态检查设置交互，不调用学校接口。
